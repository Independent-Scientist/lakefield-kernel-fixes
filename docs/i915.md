# i915 on Lakefield: GPU and the internal DSI panel

## The hardware, as the driver sees it

| what | value |
|---|---|
| SoC | Intel Core i5-L16G7, family 6 model 138 (`0x8A`) |
| GPU | Gen11 GT2, 64 EU, PCI `8086:9840`, subsystem `144d:c18b` |
| Platform support in i915 | **none.** No `INTEL_LAKEFIELD`, zero `lkf`/`lakefield` hits in `i915_drv.h`, `i915_pci.c`, `intel_display_device.c` |
| PCH | **none.** Lakefield is the only Intel SoC with no south bridge; `INTEL_PCH_TYPE()` is `PCH_NONE` |
| Display engine | Gen11.5, **four** pipes — not the three-pipe Gen11 that the ICL/EHL descriptor assumes |
| Internal panel | MIPI **DSI** (not eDP), 1920x1080, 4 lanes, RGB888, video mode, `pclk=147900`, non-burst sync events |
| Firmware | VBT `PORT_A=0 PORT_D=1 DSI=1`; `revid 0x03` is outside `jsl_ehl_steppings[]`, so stepping prints as `N/A` |

`8086:9840` has never been in i915's device table in any kernel checked (5.15,
6.6, 6.12, 7.2.14: 365 aliases, zero `9840`). linux-hardware's page for the PCI
ID lists exactly one driver match across all kernels — `CONFIG_SND_HDA_I915`,
the audio side. No DRM driver has ever claimed the device.

So out of the box: `card0` is `simple-framebuffer`/simpledrm over the UEFI
framebuffer, 3D is llvmpipe, and the panel is driven by whatever the firmware
left on screen.

## Impersonation, and why it is the only tractable route

A "proper" Lakefield port means declaring a platform and touching dozens of
`IS_*()` sites. The practical route is to tell i915 this is an Elkhart Lake part.
That is a lie, and the README of a repo like this should say so: the entry is not
correct and never will be.

`ehl_info` was chosen over `icl_info` on evidence, not on the marketing family:

- the engines that register are `bcs0 rcs0 vcs0 vecs0` — four, **no `vcs2`**.
  That is EHL's mask; ICL has a VCS2 video-enhance engine.
- the GT frequency table read from Lakefield's own fuses comes out right:
  `gt_max_freq 500`, `gt_RP0 500`, `gt_RP1 200`, `gt_RPn 300`, `rc6_enable 1`.
  Lakefield is 200 MHz base / 500 MHz boost, so the GT is reporting real
  capabilities rather than defaults.
- 36-bit PPGTT, same as EHL.

A phantom engine or a wrong fuse table is what "borrowed the wrong platform"
looks like. Both matched, so the impersonation is behaviourally right.

`icl_info` was built and tested too: it binds, but the engine mask is wrong for
this part.

## Two device tables, not one

This is the trap that eats an evening. i915 selects a device twice, from two
independent tables:

| purpose | file | table | symptom without an entry |
|---|---|---|---|
| bind the PCI driver, supply `intel_device_info` (GT, engines, PPGTT) | `i915_pci.c` | `pciidlist[]` | nothing binds: no card, no `renderD128` |
| select the **display** descriptor | `display/intel_display_device.c` | `intel_display_device_ids[]` | driver binds, 3D works, display init **silently skipped** |

The second failure is invisible by design — `find_platform_desc()` returning NULL
logs through `drm_dbg_kms`, which is off at default log level:

```c
	desc = find_platform_desc(pdev);
	if (!desc) {
		drm_dbg_kms(display->drm, "Unknown device ID %04x; disabling display.\n", ...);
		goto no_display;
	}
```

`HAS_DISPLAY()` (`pipe_mask != 0`) is then false: no `cardN-*` connectors, no
fbdev, and `debugfs/dri/0/` holds only GT files. It reads exactly like "display
fused off on this SKU". Enumerate both tables before patching, not after a failed
run: `grep -rn "INTEL_EHL_IDS(" drivers/gpu/drm/i915/` returns exactly these two.

## The seven defects, in the order they appear

### 1. No PCI ID (patches 0001)

Covered above.

### 2. `MISSING_CASE()` compiles to `UD1`

`icl_get_procmon_ref_values()` read `PORT_COMP_DW3` and switched on the PHY
process/voltage strap bits. Before the PHY is powered the read returns
`0xffffffff` (it simply does not land), which reaches `default:`:

```c
	default:
		MISSING_CASE(val);
		fallthrough;
```

`MISSING_CASE()` is `WARN(1, ...)` with a constant-true condition, so GCC proves
the following case unreachable and emits `UD1` (bytes `0f b9`) — an
invalid-opcode oops, not a warning:

```
BUG: unable to handle page fault ... RIP: icl_get_procmon_ref_values+0xe2
Code: ... 0f b9 ...
```

That oops wedges the display subsystem hard enough to need a power cycle (the
`insmod` is killed with exit 137, kworkers sit in `D`, refcount pinned). Return a
default entry explicitly; never leave a `fallthrough` after a constant-true
`WARN()`.

### 3. NULL `pch_hpd`

For `DISPLAY_VER >= 11` non-TC ports, DDI init publishes
`lpt_digital_port_connected()`. That reuse is intentional, not a PCH mismatch —
do not "fix" the PCH type, that trail is a dead end. The function reads
`display->hotplug.pch_hpd[hpd_pin]`, but `intel_hotplug_irq_init()` returns early
when `!HAS_PCH_SPLIT`, so `pch_hpd` is NULL and the index faults at address
`0x10` (NULL + 4×4).

There is no south HPD register to fall back to: `DEISR` (`0x44000`) is not
implemented on this part and reading it only produces
`Unclaimed read from register 0x44000`. Report the port as disconnected. The
internal panel does not use HPD.

### 4. Backlight went down the legacy path

`intel_backlight_init_funcs()` gives GLK/BXT `bxt_pwm_funcs` and `PCH_CNP+`
`cnp_pwm_funcs`. With `PCH_NONE`, EHL falls through to the legacy i9xx tables,
which read and write PCH backlight registers that do not exist
(`Unclaimed read from register 0x61254`) — so brightness writes do nothing and a
perfectly good panel looks dead.

Route PCH-less EHL to `bxt_pwm_funcs`. The BXT SoC PWM registers
(`0xC8250`/`54`/`58`) do land on this silicon, and `max_brightness` becomes 6400
instead of 1000 — a useful tell that the switch took effect.

### 5. PW_2 is fused off

`hsw_wait_for_power_well_enable()` times out for PW_2 on every boot. Measured:

```
pwr_ctl     = 0xf3      -> idx0/idx2/idx3 set REQ+STATE, idx1 (PW_2) sets NEITHER
fuse_status = 0x8d800000 -> PG0/PG1/PG3/PG4 distributed, PG2 clear
```

The hardware silently drops PW_2's enable request. PW_2 is the superset well
carrying PIPE_B, TRANSCODER_A/B/C, DDI lanes B–F, VGA, AUX, AUDIO and
TRANSCODER_VDSC_PW2.

Correct criterion: after a timeout, read `HSW_PWR_WELL_CTL_REQ(pw_idx)`; if the
request bit did not stick, the gate is absent on this SKU. Log and continue.

**Never use `SKL_FUSE_PG_DIST_STATUS` for this.** That bit also reads 0 for a gate
that is merely powered off, so skipping on it is circular: an earlier attempt
skipped the real PW_3/PW_4, the display lost power and the screen went dark. The
value even varies between runs (`0x8d800000` vs `0x8c000000`) with power state.

### 6. The actual panel fix: the MCD D-PHY

Lakefield's D-PHY is a **Modular Configurable D-PHY (MCD)**. Lakefield PRM Vol 12
says it plainly: "non-VPG DPHY and, therefore, has a new programming model".
Non-VPG means the hardware does **not** self-configure — software must program
the lanes. i915 only knows the VPG (Ice Lake) D-PHY and has zero references to
any MCD register (`CBBS_CLOCK_CTRL`, `DBBUDLN_*`, `DBBSUPAR_*`, `TXLP`,
`MST_SLV_INIT`: 0 files).

Worse, the ICL register layout **aliases** the MCD one, so the ICL programming
corrupts it. Firmware reference state vs i915 after `icl_combo_phys_init()`:

| register | firmware (panel lit) | i915 after PHY init |
|---|---|---|
| `0x162030` CBBS_CLK | `0x0c518d00` | `0x0c518d00` (survives) |
| `0x162290` TXRX_CTL | `0x00001c0b` | `0x00000c0b` (bit 12 lost) |
| `0x162294` MST_SLV | `0x00000001` | `0x000000fb` (**clobbered**) |
| `0x162298` TX_TIMING0 | `0x08110505` | `0x00000000` (**zeroed**) |
| `0x16229c` TX_TIMING1 | `0x0a000011` | `0x00000000` (**zeroed**) |
| `0x1622a0` TX_TIMING2 | `0x017f0001` | `0x017f00fa` (clobbered) |

`0xfb` is the tell: `ICL_PORT_TX_DW5_LN(0)` reads back `0xfb` on this machine,
and that ICL register **is** `DBBUDLN_MST_SLV_INIT_CTL` here. With
`TX_TIMING_CTL0/1` at zero the lanes have no TX timing and nothing leaves the
PHY.

MCD map (PRM Vol 12, "MCD Programming"), all inside the combo-PHY window:

```
CBBS group  +0x030  CBBS_CLOCK_CTRL_REG  bits[27:26]=11b HS clock L+R, bits[18:15]=3h TX word clock /8
per lane, UDLN base = 0x162280 + lane*0x200, lanes 0..4:
    +0x08 SOFT_RST_CTL        +0x10 TXRX_CTL        +0x14 MST_SLV_INIT_CTL (program 1)
    +0x18 +0x1c +0x20 +0x24   TX_TIMING_CTL0..3
Lane order: 0,1,3,4 = data lanes 0..3;  lane 2 = CLOCK lane
```

Per-lane firmware values (captured on the first i915 load after a boot):

```
lane0 (data0/AUX): ctl=0x1c0b mst=1 t0=0x08110505 t1=0x0a000011 t2=0x017f0001 t3=0x00030200
lanes 1,3,4:       ctl=0x0c0b mst=1 t0=0x08110505 t1=0x0a000011 t2=0x017f0001 t3=0x00030200
lane2 (CLOCK):     ctl=0x0c0b mst=1 t0=0x08230505 t1=0x0a001711 t2=0x017f0001 t3=0x00030200
CBBS_CLOCK_CTRL_REG = 0x0c518d00,  SOFT_RST_CTL = 0 for every lane
```

The alias, concretely: `ICL_PORT_TX_DW2_GRP(PHY_A)` is `0x162000+0x680+8` =
`0x162688` = lane 2's `SOFT_RST_CTL`, and `ICL_PORT_TX_DW5_LN(0,PHY_A)` is
`0x162894` = lane 3's `MST_SLV_INIT_CTL`. Clear `SOFT_RST_CTL` explicitly as
well: i915's swing/pre-emphasis write leaves `0x18` there, which are the UDLN
reset / TXLP latch override bits — a clock lane held in reset means no clock and
no image.

The restore goes in `gen11_dsi_enable_port_and_phy()`, immediately after
`gen11_dsi_setup_dphy_timings()` and before `gen11_dsi_enable_ddi_buffer()`,
matching the PRM order (configure D-PHY, then enable the IO buffer). Verified:
the writes stick on all five lanes and still hold at the end of `pre_enable`, so
nothing re-clobbers them later.

### 7. Two DCS reads after the transcoder is programmed

`gen11_dsi_pre_enable()` sends `GET_POWER_MODE` (`0x0a`) and `GET_DISPLAY_ID`
(`0x04`) after `gen11_dsi_set_transcoder_timings()`. `gen11_dsi_host_transfer()`
ends with `//TODO: add payload receive code`, so these never return data — but
the build with them lights the panel and a build without them did not.

That comparison is not clean (the second build also had the backlight at 0, which
by itself is a black screen), so the honest statement is: keep them, they were in
the build that worked, and nobody has isolated whether the traffic or the delay
is what matters.

## Verified working state

On the reference machine, with the series applied and the module installed:

```
/sys/class/graphics/fb0/name                        -> i915drmfb
/sys/class/drm/card1-DSI-1/status                   -> connected
/sys/class/drm/card1-DSI-1/enabled                  -> enabled
/sys/class/backlight/intel_backlight/max_brightness -> 6400
/dev/dri/                                           -> card1, renderD128
i915_display_info:  [CRTC:111:pipe A] enable=yes active=yes mode="1920x1080":60
                    [ENCODER:269:DSI A] -> [CONNECTOR:270:DSI-1]
                    [PLANE:35:plane 1A] hw: [FB:286] XR24 1920x1080, visible=yes
```

A whole-PHY diff against the firmware's working state agrees: 624 registers
compared across `0x162000`–`0x162b3c`, 2 differ and both are status registers.
`TRANS_DDI_FUNC_CTL` (`0x6b400`) is `ENABLE|pipeA|width3`, `DDI_BUF_CTL`
(`0x64000`) is `ENABLE` with `IS_IDLE` (bit 7) clear — the buffer really is
driving.

Read these live with `intel-gpu-tools` instead of rebuilding:

```sh
sudo intel_reg read 0x6b400 0x6b030 0x64000 0x162688
```

`0x6b400` = TRANS_DDI_FUNC_CTL (ENABLE = bit 31, EDP_INPUT bits 12–14,
PORT_WIDTH bits 1–3); `0x64000` = DDI_BUF_CTL (ENABLE bit 31, IS_IDLE bit 7 —
clear means driving).

## 3D and Mesa: a second, independent gate

Binding the driver proves nothing to userspace. Mesa refuses unknown devids from
`include/pci_ids/iris_pci_ids.h`:

```
MESA: warning: Driver does not support the 0x9840 PCI ID.
```

`INTEL_FORCE_PROBE` does **not** help: it forces devices already in the table
that are marked `require_force_probe`, not unknown ids. Tested, no effect.

The table is checked-in data, rows of `CHIPSET(id, family, fam_str, name)`.
Add one row in the EHL/JSL block:

```c
CHIPSET(0x9840, icl_gt2, "LKF GT2", "Intel(R) UHD Graphics")
```

`icl_gt2` for the 64-EU Gen11 GT2 topology; `ehl_2x8` is the alternative if ICL
workarounds misbehave on the LP part. The renderer string is literally this
row's `fam_str`, so it doubles as proof that the patched table is what loaded:

```
OpenGL core profile renderer: Mesa Intel(R) UHD Graphics (LKF GT2)
OpenGL core profile version:  4.6 (Core Profile) Mesa 26.2.6
```

`tools/gl-probe.c` then proves **execution** rather than context creation: it
compiles a vertex+fragment shader, draws a triangle into an FBO and reads the
pixel back (`pixel@32,32 = rgba(0,255,0,255)`, `glerr=0x0`, `RESULT: PASS`).

`eglinfo -B` only proves a context exists. A renderer string means "the driver
loaded"; a shader draw plus `glReadPixels` means "the GPU executes". They are
different claims — keep them apart when reporting status.

### Installing a patched Mesa on Arch is its own trap

- Arch ships **one** monolithic `/usr/lib/libgallium-<ver>-arch1.1.so` containing
  every gallium driver, and every `/usr/lib/dri/*_dri.so` is a 14-byte symlink to
  one megadriver. There is no per-driver `iris_dri.so` to replace. So build with
  `-Dgallium-drivers=iris,llvmpipe`, not `iris` alone, or llvmpipe disappears
  along with everything else.
- **Versioned symbols must match.** Arch's shim resolves
  `dri_create_drawable@@libgallium-26.2.6-arch1.1.so` including the version name;
  a library built as `libgallium-26.2.6.so` can never satisfy it, the load fails
  and glamor reports `couldn't get display device`. Mesa derives both the soname
  and symbol version from `meson.project_version()` (the `VERSION` file), so set
  `VERSION` to the distro's exact string (`26.2.6-arch1.1`), reconfigure, rebuild.
  Check with `nm -D` before installing.
- **GLX takes its renderer from the X server's Mesa, not the client's.** A
  patched build tree under `meson devenv` never shows up in `glxinfo`; that is not
  a build failure. Measured here: `glxinfo` under `meson devenv` printed
  `llvmpipe (LLVM 23.1.4)` while the same driver rendered correctly through the
  render node.
- Back the old libgallium up first. One file, one-file rollback.

With it installed, Xorg reports what you want:

```
(II) modeset(0): glamor: Using OpenGL 4.6 context.
(II) modeset(0): glamor X acceleration enabled on Mesa Intel(R) UHD Graphics (LKF GT2)
(II) modeset(0): [DRI2]   DRI driver: iris
```

## Status of this patch set, precisely

- The seven patches apply cleanly, in order, to a pristine `linux-7.2.14` tree.
- That tree builds (`make M=drivers/gpu/drm/i915 modules`) into an `i915.ko`
  whose vermagic is `7.2.14-arch1-1 SMP preempt mod_unload`, which carries the
  `9840` alias and the MCD register constants, and which contains none of the
  bring-up instrumentation.
- The hardware verification described above was done with a build that carried
  the same functional changes **plus** debug logging and three experiments that
  were later shown to be irrelevant (listed in `docs/research-log.md`). The
  cleaned series has not been booted on the hardware since the cleanup; if you
  are the cautious type, build it, install it with `tools/i915/install-i915.sh`
  (which keeps the old module as `.orig`) and reboot — a dark panel costs one
  copy and one reboot to roll back.

## What a real port would need

- A `lakefield_info` / `lakefield_desc` describing four pipes and the real
  display engine, instead of pretending to be EHL.
- An MCD D-PHY programming path in the DSI code, keyed on platform rather than
  on hardcoded `0x162xxx` offsets, with the PRM's lane map.
- PCH-less handling in HPD, backlight, power wells and VBT interpretation as
  platform capabilities rather than `if (platform == ...)` special cases.
- VBT/stepping handling for `revid 0x03` (currently `STEP_UNKNOWN`).

That is a lot of work and none of it is done here. This repo is a working
starting point, not a submission.
